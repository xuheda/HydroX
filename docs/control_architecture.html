定位

HydroX 是 OceanX 的自动驾驶仪运行时。它负责导航估计、制导控制、控制分配、执行器输出、DDS 状态发布和 QGC telemetry。Unreal/UE 负责场景、渲染、查询、碰撞环境和仿真传感器；AUV/ROV/USV 主运动由 Fossen body 积分，空中载具由 Aero body 积分。ROS 2 位于任务、策略和工具层，只通过 HydroX 的 DDS topic 输入 setpoint 或读取状态。

这篇文档使用功能层级名：

功能层级当前实现名说明
导航估计EKF + EstimationProfile统一 18 维 aided EKF 数学核心；UUV、USV、UAV Profile 选择观测、环境速度语义以及 Q/R/P0。
制导控制GNC / IController根据 vehicle archetype 选择不同控制器。
控制分配IAllocator把广义力 tau 映射到归一化执行器通道。
自动驾驶仪运行时HydroX runtimeSITL 已使用共享周期调度和命令权限门控；Pixhawk 6C HITL 将注入 NuttX 平台适配并复用这些行为。

UE 侧不应新增 PID、reward 或任务状态机来绕过 HydroX 控制链路。任务策略可以决定目标、模式和 setpoint，但不直接控制 UE actor。

闭环链路

控制命令链路：

ROS 2 任务 / 策略 / 操作员设定值
  -> /oceanx/{vehicle}/control/setpoint_sources/{source}
  -> setpoint_mux（控制权、优先级、超时与失效保护）
  -> /hydrox/{vehicle}/in/setpoint (GNCSetpoint，唯一 Publisher)
  -> Micro XRCE-DDS / DDS Agent
  -> hydrox_sitl
     -> 导航估计输出 state
     -> 制导控制生成 tau
     -> 控制分配生成 normalized actuator channels
  -> MAVLink HIL_ACTUATOR_CONTROLS (93)
  -> FOceanXCommBridge command queue
  -> FOceanXSimulationRuntime fixed-step command drain
  -> active FOceanXDynamicsBody 重建执行器力和力矩
  -> FOceanXFossenBody 或 FOceanXAeroBody fixed-step integration
  -> UE Actor transform follows active body state

状态反馈链路：

active Fossen/Aero body StateSnapshot / UE sensor snapshot
  -> UE 传感器层
  -> UOceanXSensorPhaseComponent
  -> FVehicleState.NavigationSensors
  -> FOceanXCommBridge
  -> MAVLink HIL_SENSOR / HIL_GPS / HIL_DVL
  -> hydrox_sitl SensorAdapter
  -> 导航估计
  -> 制导控制
  -> DdsPublisher
  -> /hydrox/{vehicle}/out/*
  -> ROS 2 任务 / 策略 / 诊断节点

声学通信、被动声呐和 RF 通信属于 OceanX 传感器读数，不属于 HydroX 导航估计主状态。它们可以供策略层使用，但不应绕过 HydroX 直接改自动驾驶仪状态。

真值隔离

正常控制闭环固定使用 EKF NavigationState。HIL_TRUTH_STATE 即使新鲜有效，也只进入 XLog 和 estimator debug 通道；只有显式开启 --publish-truth-state true 才发布到 DDS 真值 topic，任何一种诊断出口都不会自动替换 GNC 反馈。默认配置为 --control-feedback-source estimated_state、--publish-truth-state false、--allow-truth-heading-aid false。

--control-feedback-source truth_debug 只用于显式的仿真控制器隔离实验；该模式在启动和周期状态日志中标记 TRUTH_DEBUG，其结果不能作为估计器闭环验证。OceanX 侧还必须显式启用 -OceanXSendHilTruthTelemetry=true，并且只允许 full-stack 仿真运行。真值发布、真值航向辅助和真值控制反馈是三个独立开关，任何一个都不会隐式开启另一个。

运行循环

HydroX SITL 默认以：

--rate 100

运行。HydroX 控制核心采用统一的输入时间戳契约；--rate 只声明名义控制频率，用于首个控制周期的初始化 dt 和按控制周期计数的低频遥测。连接建立后，每个严格递增的 HIL_SENSOR.time_usec 恰好推进一次导航估计、制导控制、motor model 和 energy model，后续积分 dt 直接取相邻输入时间戳之差。同一次 TCP 读取中的多个 IMU 样本按时间戳排队处理，不合并为一次控制更新。平台单调时间仅用于 DDS 命令接收时间、命令 freshness/timeout、心跳、断线保护和 socket 等待，不推进控制状态。HydroX 回送的 HIL_ACTUATOR_CONTROLS.time_usec 由 UE 固定步物理线程校验。完整仿真时间与频率契约见 OceanX 仿真时间与频率契约。

每个自动驾驶仪 tick 的核心顺序是：

  1. 等待 UE TCP HIL 链路出现可读数据，不使用该等待时间推进控制状态。
  2. SensorAdapter 解析并缓存 HIL_SENSOR、HIL_GPS、HIL_DVL 和调试用 truth frame。
  3. 每个严格递增的 IMU timestamp 形成一个独立控制输入；重复或倒退的 timestamp 被拒绝。
  4. 以相邻输入 timestamp 之差计算算法 dt。
  5. ControlSessionGate 在本连接代次首次收到有效传感器后开放新命令入口。
  6. 非阻塞轮询 DDS setpoint，并按 DDS/HIL 会话代次和平台单调接收时间检查有效性。
  7. 导航估计更新内部 NavigationState 和 covariance。
  8. IController 根据当前 state、mode 和 setpoint 生成广义力 tau=[X,Y,Z,K,M,N]。
  9. IAllocator 将 tau 映射为归一化执行器通道。
  10. 通过 MAVLink HIL_ACTUATOR_CONTROLS 发回 UE。
  11. 发布 /hydrox/{vehicle}/out/* 状态、传感器快照、执行器输出、odom 和 tf；没有新输入 timestamp 时不执行控制更新。

源码入口：HydroX/apps/sitl/main.cpp；共享运行时接口位于 HydroX/include/hydrox/runtime/，平台适配位于 HydroX/platform/。

导航估计

当前导航估计核心是统一的 18 维 aided EKF。状态向量使用 NED / FRD / SI：

x = [
  N, E, D,
  roll, pitch, yaw,
  u, v, w,
  b_ax, b_ay, b_az,
  b_gx, b_gy, b_gz,
  m_N, m_E, m_D
]

m_N,m_E,m_D 是环境介质速度：UUV/USV 中表示水流；UAV 中保留风速语义，但在没有空速或气动相对速度观测时明确禁用并保持 invalid。

输出状态：

eta = [N, E, D, roll, pitch, yaw]
nu  = [u, v, w, p, q, r]

估计传感器来源

所有进入 HydroX 导航估计闭环的测量，原则上来自 OceanX UE 仿真传感器，再经 MAVLink HIL 进入 HydroX。ROS 2 不发布估计器内部测量，也不把 truth 直接写进自动驾驶仪状态。主线 HIL 实现中，ImuSensor、DepthSensor、DvlSensor、GpsSensor 和 MagnetometerSensor 在传感器 tick 中按各自频率唤醒，并用当前 fixed-step sample_time 从 FVehicleState history 读取本载具状态，更新各自 latest sample buffer；随后本载具 UOceanXSensorPhaseComponent 统一读取这些 latest sample，按传感器分别写入 FVehicleState.NavigationSensors.Imu/Depth/Magnetometer/Dvl/Gps，每个 sample 都保留自己的 TimestampSec 与 bValid。FOceanXCommBridge 在通信线程只读取 snapshot 并编码 MAVLink，不再根据 physics truth 重新合成 IMU、DVL、GPS、压力或磁场。

HIL_SENSOR.time_usec 对应 IMU sample time。深度和磁力计虽然也通过 HIL_SENSOR 传输，但只在存在未发送过的近时刻 sample 时才置 fields_updated，避免低频测量被每个 IMU frame 重复当作新测量。HIL_DVL.time_usec 和 HIL_GPS.time_usec 分别对应 DVL/GPS 自己的 sample time，HydroX SensorAdapter 后续按这些 timestamp 计算 age、timeout 和融合时刻。

磁力计、DVL、压力深度是当前水下 UUV 主线最关键的估计输入。GPS 在水面或近水面定位辅助时有效；深水闭环不应依赖 GPS。声学定位、USBL/LBL 等如果后续加入，应作为具名传感器和 HIL/DDS 边界输入，而不是让 ROS 策略节点直接改内部 NavigationState。

当前 HydroX SensorAdapter 已经把 IMU、bottom/water DVL、depth、GPS、magnetometer 和 debug truth 统一整理为带 source、frame、timestamp、validity、age 和 covariance/variance 的 measurement 结构，再由 EstimationProfile 做平台语义门控。EKF 的状态包含 body-frame 对地速度与 world-NED 环境介质速度：bottom DVL 直接约束前者，water DVL 约束两者之差，GPS NED 速度提供对地参考，因此在水体跟踪且存在 GPS 速度时可估计真实流速。每个 DVL/GPS timestamp 只允许一次 measurement update，拒绝的异常帧也不会在之后的高频 IMU tick 重试。DVL、depth、GPS 和 debug truth 的 age/timeout 使用输入 measurement timestamp 计算，不使用平台墙钟，因此仿真暂停、慢放或加速不会改变测量时效；真实传感器驱动也遵循同一 timestamp 契约。仅有水体 DVL、没有 GPS 或近时刻底跟踪时，流速与对地速度不可完全观测；滤波器保留估计但让其 covariance 随过程噪声增长，NavigationState.medium_velocity_valid 会据此反映可信度。无 accelerometer mechanization 时，相对介质速度和 GPS 速度更新冻结直接姿态雅可比，避免在不可观条件下用速度歧义旋转载具姿态。GPS 的 lat/lon/alt 会按 --gps-origin-lat-deg / --gps-origin-lon-deg / --gps-origin-alt-m 转回本地 NED；UE 自动拉起 HydroX 时会传递与 OceanXGpsOrigin* 相同的 origin，手动启动时需要显式保持一致。ROS/DDS setpoint freshness 与 timeout 始终使用 sample 到达 HydroX 时记录的平台单调时间，这是所有运行环境共同采用的通信权限规则。固定 R 仍作为非法 covariance 的 fallback。

控制输入与模式

HydroX 的权威低层输入是：

/hydrox/{vehicle}/in/setpoint

类型为 oceanx_interfaces/msg/GNCSetpoint，在 HydroX 内部对应：

depth_ref        目标深度，m，NED down 为正
heading_ref      目标航向，rad
surge_ref        目标纵向速度，m/s
use_yaw_rate_ref 是否启用 yaw-rate 控制
yaw_rate_ref     目标 yaw rate，rad/s
wp_n/wp_e/wp_d   3D waypoint，NED
mode             DISABLED / DEPTH_HOLD / WAYPOINT_3D / DP / SURFACE

模式语义：

模式含义控制行为
DISABLED安全空闲输出零 tau，执行器不 armed。
DEPTH_HOLD深度、航向、速度保持使用 depth_ref、heading_ref 或 yaw_rate_ref、surge_ref。
WAYPOINT_3D3D 航点控制器把 waypoint 转成局部 heading/depth/speed 目标。
DP动态定位仅对 Thruster / ROV 可悬停平台承诺；使用 wp_n/wp_e/wp_d 和 heading_ref 生成位置保持 wrench。鱼雷型 AUV 不承诺 true DP。
SURFACE水面模式深度/俯仰积分清零，保持水面航向和速度。

兼容入口：

/oceanx/{vehicle}/control/manual_twist

类型为 geometry_msgs/Twist，由 adapter 转成 GNCSetpoint 并发布到 /oceanx/{vehicle}/control/setpoint_sources/manual。它适合 teleop 或临时测试，由 setpoint_mux 负责和其他控制源仲裁，不再直接发布 /in/setpoint。

控制方法

HydroX 不是为每个载具编写一套独立 controller，而是根据 vehicle profile 选择一个控制原型和一个 allocator。载具参数、执行器限制和几何布置来自 VehicleBundle、vehicle profile 及所选 Fossen/Aero 后端参数。

Vehicle archetypeController主要方法适用对象
Slender-body AUVSlenderBodyAUVControllerdepth 外环 PID 生成 pitch_ref，pitch PID 生成 M，heading SMC 或 yaw-rate PI 生成 N，surge P 生成 XEcaA9 / LAUV 这类鱼雷型 AUV
Thruster / ROVThrusterVehicleControllerDEPTH_HOLD 下跟踪 surge/depth/heading；DP 下把 wp_n/wp_e/wp_d 位置误差旋到 body FRD，生成 surge/sway/heave/yaw wrenchRexROV2、DesistekSaga、悬停型 AUV
SurfaceSurfaceVesselControllersurge PD + yaw heading/yaw-rate 控制，waypoint 时转成平面 heading 和 surgeUSV
MultirotorMultirotorControllerdepth/height、XY waypoint、roll/pitch/yaw 控制，生成 collective thrust 和 momentsUAV multirotor
Fixed wingFixedWingControlleraltitude/depth 转 pitch_ref，course 转 roll_ref，输出速度/姿态类 demandUAV fixed wing
VTOLVtolController低速旋翼高度/姿态控制与前向速度 demand，配合过渡区机翼/前推桨StandardVTOL

鱼雷型 AUV 的深度控制不是直接输出 heave force。它通过 depth 外环给出 pitch_ref，再通过 pitch moment 和前进速度产生升沉效果：

depth error -> DepthPID -> theta_ref
theta_ref - pitch -> PitchPID -> tau_M
surge_ref - u -> SurgeP -> tau_X
heading_ref / yaw_rate_ref -> HeadingSMC or yaw-rate PI -> tau_N
tau_Z = 0

这意味着低速时舵效会下降，因为 allocator 依赖动压 q=0.5*rho*u^2。如果 AUV 低速深度跟踪差，应先检查 surge、DVL 速度估计、舵面饱和和 Fossen 参数，而不是简单把 depth PID 调大。

更详细的底层控制方法见 控制方法。

控制分配

控制器统一输出 body-frame 广义力：

tau = [X, Y, Z, K, M, N]

单位为 N 和 N*m。allocator 将 tau 映射为 MAVLink HIL_ACTUATOR_CONTROLS 需要的归一化通道：

Allocator映射方式
FinAllocatorX 转 stern prop thrust/rpm，M 转水平舵面，N 转垂直舵面，通道 0..4 为 4 个舵面 + 推力。
ThrusterMatrixAllocator根据 thruster 位置、方向和 max thrust，把 6-DOF wrench 映射到多推进器通道。
TwinScrewAllocator把 surge force 和 yaw moment 映射到左右推进器。
QuadrotorAllocator把 collective thrust 和 moments 映射到四旋翼电机通道。
FixedWingAllocator把速度、roll、pitch、yaw-rate demand 映射到固定翼控制通道。
VtolAllocator通道 0..3 为升力旋翼，4..6 为 elevator/aileron/rudder，7 为前推桨。

输出契约：

normalized channel in [-1, 1]
  -> MAVLink HIL_ACTUATOR_CONTROLS
  -> UE vehicle profile
  -> actuator wrench
  -> selected Fossen or Aero dynamics and kinematic integration
  -> UE Actor transform

通道符号必须在三处保持一致：HydroX allocator、MAVLink bridge、UE vehicle profile。新增载具时优先新增/修改 profile 和 allocator 参数，只有可控自由度或控制结构确实不同，才新增 controller。

ROS 2 接口边界

Topic、Service、Action、QoS、发布频率、frame、超时和控制源优先级已拆分到独立的 OceanX ROS 2 话题与接口契约。该文档是 ROS/DDS 接口的唯一权威说明；本页只保留理解 HydroX 控制闭环所需的接口引用。

/hydrox/{vehicle}/...  # HydroX 自动驾驶仪 ABI
/oceanx/{vehicle}/...  # OceanX 上层、仿真传感器和 ROS 工具
/oceanx/fleet/...      # 跨载具任务与编队接口

需要进入自动驾驶仪闭环的导航测量走 MAVLink HIL → HydroX；ROS 任务和策略通过 setpoint_mux 向 /hydrox/{vehicle}/in/setpoint 提交最终命令。ROS 侧不得直接改 HydroX 内部估计状态，也不得从当前队友真值重新模拟声学传播。

归属总结

  • hydrox_sitl 负责导航估计、制导控制、控制分配、MAVLink HIL 和 /out/* telemetry topic。
  • UE FOceanXCommBridge 负责把 UE 仿真传感器 sample 编码成 HIL 消息，并消费 HydroX 执行器输出。
  • oceanx_control 负责 mission 消费和 setpoint 发布。
  • oceanx_coordination 负责跨载具 mission assignment 和 formation service 入口。
  • direct_cmd_adapter 是给轻量外部控制器使用的可选兼容节点。
  • 所有依赖估计状态消息类型 VehicleState 的外部控制节点必须使用本地 monotonic receive time 检查状态新鲜度；setpoint_mux 再做一次独立状态闸门。状态失联会清空缓存，恢复时必须先收到新状态、再收到新命令，禁止重放失联前的 source sample。
  • OceanX 声学、RF、被动声呐等策略传感器应由 UE sensor layer 生产 typed reading，ROS 侧只转发，不重新模拟。

扩展规则

  • 新几何或新执行器布置应新增 vehicle profile。
  • 只有可控自由度或控制结构不同，才新增 controller。
  • actuator limit、effectiveness matrix 和所选 Fossen/Aero 后端参数保持在配置中。
  • 估计器测量必须来自具名传感器和 HIL/DDS 边界，不能让策略节点直接写自动驾驶仪 state。
  • truth state 只能用于日志、诊断和对齐测试；UE 侧默认不发送 HIL_TRUTH_STATE，只有显式传入 -OceanXSendHilTruthTelemetry=true 时才发送。-OceanXPublishSitlTruthState=true、-OceanXAllowTruthHeadingAid=true 与 -OceanXControlFeedbackSource=truth_debug 分别控制 DDS 诊断发布、航向辅助和真值调试闭环，三者互相独立并且都要求先开启真值遥测。正式闭环必须保持 estimated_state。
  • 坐标转换留在 MAVLink、DDS 或 ROS 边界。
  • 新增或修改 ROS/DDS 接口时，按 ROS 2 接口维护规则 同步 manifest、interface、QoS、频率、文档和测试。
  • controller 输出、allocator 饱和、MAVLink channel 和 UE actuator 符号要一起测试。
